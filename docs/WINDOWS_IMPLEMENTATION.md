# Windows implementation (`VSoft.Process.Windows.pas`)

Maintainer notes on how `TWindowsProcess` launches, monitors and tears down a child. User-facing behaviour is documented in the README; this file explains *why* the code is shaped the way it is.

Win32 names are used below. Where older Delphi versions lack a declaration, the code calls a prefixed copy from `VSoft.Process.WinAPI.pas`: `TVProcStartupInfoExW`, `VPROC_PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, `VPROC_FILE_FLAG_FIRST_PIPE_INSTANCE`, `VPROC_PIPE_REJECT_REMOTE_CLIENTS`, `VPROCESS_CREATE_BREAKAWAY_FROM_JOB`, `VProcCreateProcessW`, `VProcCancelIoEx`, `VProcCancelSynchronousIo` and `VProcReadFile`. The threadpool I/O and attribute-list APIs are imported statically, so Windows Vista is the minimum.

## Run lifecycle (shared with POSIX, `VSoft.Process.Base.pas`)

1. `Execute`, `ExecuteAsync` and `ExecuteDetached` raise `EInvalidOpException` while `FCompletionEvent` is unsignalled (a run is in progress), or while another thread holds `FRunClaim`. `ClaimRun` takes that claim (an interlocked flag) before checking the event, and it is released once `FCompletionEvent` has been reset (or the start has failed), so two threads can't both get past the check before either has marked the run as in progress. Otherwise they reset status, then return False (with the reason in `Errors`) if the cancellation token or event is already signalled or validation fails. The rule that rejects `TerminateOnTimeout = False` with `JobMode = KillOnRelease` is checked in `StartRun`, not in `ValidateStartUpBuilder`, so `ExecuteDetached` (which ignores both) is not subject to it. `StartPipeTargets` then snapshots the configured targets, injects default encodings and calls each target's `Start` once.
2. `DoCreateProcess` launches the child. If it fails or raises, `AbortStart` calls `Done` on every started target and signals completion.
3. `RunWorker` (on the caller's thread for `Execute`, on an anonymous thread for `ExecuteAsync`) calls `DoWaitForCompletion`, which must deliver all output and release every handle and thread before returning. It then calls `StopPipeTargets` and `CompleteRun`, which publishes ExitCode/TimedOut, clears the cancellation references, publishes `Status` and finally sets `FCompletionEvent`. Only after that does it fire `OnExit`.
4. Handler exceptions. `OnStarted` fires between steps 2 and 3, on the thread that called `Execute*`. If the handler raises there, `InternalStart` / `InternalStartAsync` set `FTerminateEvent`, run `RunWorker` on that same thread (which stops the child and completes the run as in step 3) and only then re-raise, so the caller never gets an exception with a run still in progress. `ExecuteAsync` takes the same path when the monitor thread can't be created. `RunWorker(raiseToCaller)` passes what `OnExit` raises on to the caller of a synchronous `Execute`; on the `ExecuteAsync` worker thread, and while a run is being completed for an earlier exception, it is logged to `Errors`. A handler queued to the main thread (`MarshallEventsToMainThread`) is called inside a `try..except` that passes the exception to `ApplicationHandleException` when assigned and logs it otherwise: later RTL versions drop a queued method's exception when no handler is assigned, earlier ones raise it from `CheckSynchronize`.

Because `Status` is published last, a caller that polls `Status` sees complete output, and a new run can't start while the old one still owns resources.

`ExitCode` and `TimedOut` raise only while a detached child exists (`IsDetachedRun`: start mode `Detached` and `Status = Running`). A detached launch that was refused or failed leaves `Status` at `Idle`, and they read `$FFFFFFFF` / False as after any failed `Execute*`.

All `HandleData` calls go through `TProcessBase.ProcessStdOut` / `ProcessStdErr`, which serialise them on `FDeliveryLock`. Each call is wrapped in try/except: a target that raises is logged and skipped from then on, but the pipe keeps being read so the child never blocks on a full pipe. The fault flag is kept once per started target (`FTargetFaulted`, indexed by `TPipeTargetSlot.StartedIndex`), not per stream slot, so a target attached to both streams stops receiving from both. `StopPipeTargets` logs a `Done` (target or stdin source) that raises, a non-`Exception` object included, and carries on.

The configured targets can be detached with `ClearStdOutPipes` / `ClearStdErrPipes` / `ClearPipes` (the last also drops the stdin source). They only empty the configured lists; a run in progress works on its own snapshot (`FRunStdOut` / `FRunStdErr` / `FRunStdIn`). `result` is assigned before the lists are cleared, because a target being released may hold the last other reference to the process (a delegate that captured the `IProcess`).

`Terminate` returns False straight away when no run is in progress (including from `OnExit`, which fires after the run has completed) or the run is detached. Otherwise it sets `FTerminateEvent` and waits up to 5 s (`Terminate(waitMS)`: up to `waitMS`) for `FCompletionEvent`, returning whether the run completed in time. It doesn't wait, and returns True, for `Terminate(0)`, and when it would be waiting on itself: from the worker thread (`FWorkerThreadId`), from inside a pipe target (`FDeliveringThreadId`, set under `FDeliveryLock`), from the stdin writer (`FStdInWriterThreadId`, set before that thread starts), or from the thread that is inside `ExecuteAsync` before the async worker exists (`FStartThreadId`, which covers `OnStarted`). Any other thread waits, also during that start window.

- **Stale requests.** `FTerminateEvent` is shared by every run of the object, so each run has a number (`FRunGeneration`). `Terminate` reads it before checking that a run is in progress, and `RequestTerminate` sets the event only if the number is unchanged, under `FTerminateLock`; `ResetTerminateRequest` (new number, reset the event) takes the same lock at the start of a run. A `Terminate` overtaken by the end of its run therefore returns False and can't stop the run started after it.
- **Main thread.** `WaitForCompletion` on the main thread waits in 10 ms slices and calls `CheckSynchronize` between them, as `TThread.WaitFor` does: the run can't complete while one of its targets is blocked in `TThread.Synchronize`. Queued methods (a queued `OnExit` among them) can therefore run before `Terminate` returns, and an exception from one propagates out of `Terminate`. A `Terminate` made on the main thread from inside a synchronised method is not helped by this and waits its full time.

## Process creation

- **Console.** `Execute` / `ExecuteAsync` pass `CREATE_NEW_CONSOLE`, so a console child does not share the host's console. The one exception is a child given a console handle of the host through `InheritHostStdHandles` with `ShareHostConsole` (below): the flag is left out and the child shares our console. `STARTF_USESHOWWINDOW` shows or hides that console's window according to `HideWindow` (`SW_HIDE` by default, `SW_SHOWNORMAL` when False).
- **Pipes.** stdout and stderr use uniquely named pipes because anonymous pipes can't do overlapped I/O. The server (read) end is `FILE_FLAG_OVERLAPPED | FILE_FLAG_FIRST_PIPE_INSTANCE` with `PIPE_REJECT_REMOTE_CLIENTS`. stdin is an anonymous pipe (the parent writes synchronously), so the child gets an ordinary synchronous handle. `PipeBufferSize` (0 = 64 KB) sizes the named pipes, the stdin pipe and the read buffers. When at least one stream is redirected, a stream that isn't gets a handle to `NUL` rather than `INVALID_HANDLE_VALUE`, which would be the current-process pseudo handle. When nothing is redirected, `STARTF_USESTDHANDLES` isn't set and the child uses its new console.
  - **`TPipeSource.FileAsStdIn`** (`IFileStdInPipeSource`) replaces the stdin pipe with a non-inheritable `DuplicateHandle` of the file the source opened in `Start`, handled like a pipe end, and starts no writer thread.
  - **`InheritHostStdHandles`.** A stream that isn't redirected gets a non-inheritable `DuplicateHandle` of `GetStdHandle`. Like the pipe ends, it is made inheritable only for the spawn, added to the handle list and closed after it; with credentials it stays non-inheritable. A host without that handle (0 or `INVALID_HANDLE_VALUE`) gets `NUL`. A console pseudo-handle (low two bits set, Windows 7 and earlier), which the handle list and the Secondary Logon service reject, or a failed duplication, also gets `NUL` and is logged. `STARTF_USESTDHANDLES` is set when any stream has a pipe or a host handle.
    - **Console handles.** A console handle (`GetConsoleMode` succeeds on the copy) only works in a process attached to that console. By default the copy is closed and the stream is handled as one the host has no handle for, without a log entry (the same for a Windows 7 pseudo-handle), so the child keeps its own console and never sees our Ctrl+C. With `ShareHostConsole` the child is created without `CREATE_NEW_CONSOLE` and shares ours, and with it the console's Ctrl+C / Ctrl+Break. With credentials that is not possible (the Secondary Logon service always gives the child a new console): the copy is closed, the stream gets `NUL` and the reason is logged.
- **Handle inheritance.** Every pipe end is created non-inheritable. For the spawn the child's ends are made inheritable, the child is created, and our copies are closed. For `CreateProcessW` a `STARTUPINFOEXW` with `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` limits inheritance to exactly those handles. There is no lock around the spawn: every `CreateProcess` in the library either names the handles it passes on (that handle list) or inherits none (`bInheritHandles` False: a launch with nothing redirected, and `ExecuteDetached`), so a launch on another thread can never pick up our pipe ends while they are inheritable, and concurrent launches need no serialising. (A child that did inherit them would keep them open, and our `Execute` would not return until that unrelated child exits.) A launch with credentials makes nothing inheritable (see [Credentials](#credentials)). This only covers launches made through the library: a `CreateProcess` with `bInheritHandles` True and no handle list elsewhere in the host can still inherit them during that window.
- **Job object.** The child is created `CREATE_SUSPENDED`, assigned to a new job (`BREAKAWAY_OK`, plus `KILL_ON_JOB_CLOSE` for `JobMode = KillOnRelease`; no job at all for `NoJob`) and only then resumed, so even its first children are in the job. If the job can't be created, or the child can't be assigned to it (Win7 nested jobs, Run-As children), the error is logged, the run has no job and termination falls back to `TSystemUtils.TerminateProcessTree` plus `TerminateProcess`. Otherwise `TerminateJobObject` on an empty job would "succeed" while the child lives on. If `SetInformationJobObject` fails, that is only logged and the job is used without its limits. The job is kept after the run and closed at the start of the next `Execute` / `ExecuteAsync`, after a failed start, or when the object is destroyed, which kills anything the child left behind when the job has `KILL_ON_JOB_CLOSE`. `ExecuteDetached` does not close it.
- **Environment, directory, affinity.** An environment block is built only when `Environment.HasOverrides`; otherwise nil is passed and the child inherits ours. An empty `WorkingDirectory` is passed as nil. `ProcessorAffinity` is applied with `SetProcessAffinityMask` while the child is still suspended (a failure is logged).
- **Executable.** `ValidateStartUpBuilder` resolves `StartInfo.Executable` into `FResolvedExecutable` (`ResolveExecutable`), which is then used for `lpApplicationName`, argv[0], the batch-file check and both logon / detached paths. A name containing `\`, `/` or `:` is expanded against this process's current directory (not `WorkingDirectory`) and must exist; nothing is appended. A bare name is searched for in this process's `PATH` only (never the `PATH` in `Environment`, so the child can be given a constrained one), absolute entries only, with `.exe` appended when it has no extension; the file found is passed through `ExpandFileName` (`GetFullPathName`), which drops the trailing dots and spaces Windows ignores, so `run.cmd.` resolves to `run.cmd` and gets the batch-file checks (`IsBatchFile` also ignores them). A batch file whose resolved path contains `%` or `!` is refused, since cmd.exe expands those in its own command line. This deliberately skips CreateProcess's own search order (host folder, current directory, system folders), which would let a planted file in the current directory win.
- **Command line.** `lpApplicationName` is always the executable, and `lpCommandLine` starts with a quoted copy of it. For `.bat` / `.cmd`, CreateProcess runs `cmd.exe /c <lpCommandLine>`. Arguments containing cmd metacharacters are quoted. At validation, an argument whose name or value (ignoring one pair of surrounding quotes) or separator contains `% ! " CR LF` or NUL is rejected. The whole line gets an extra outer pair of quotes, because cmd strips the first and last quote of a `/c` command.
  - **NUL.** `CreateProcess` takes NUL-terminated strings, so a `#0` would silently cut off the rest of the command line: every later argument, and for a batch file the closing quotes that keep cmd.exe from running argument text as a command. Validation therefore refuses a NUL in `Executable`, `WorkingDirectory`, `DefaultArgumentSeparator` and in any argument's name, value or separator, for any program and for `AddUnsafeBatchRaw` text too.
  - **Name and value.** Each part is quoted on its own (`JoinNameAndValue`). Where a quoted value directly follows a name plus separator that ends in backslashes, those backslashes are doubled, since `\"` would otherwise be an escaped quote (`/out:C:\build\\"my file.txt"`). A quoted name directly followed by a quoted value (empty separator) is unescaped and quoted again as one token, since a quote right after a closing quote is a literal quote. `qtNone` parts are joined as given.
  - **Batch arguments.** `RenderBatchArgument` quotes a part by the argument's style but never escapes it for `CommandLineToArgvW`: cmd.exe does not take a backslash as an escape, so the doubled backslash before a closing quote would reach the script.
  - **Raw arguments.** An `AddUnsafeBatchRaw` argument is exempt from that validation (except for NUL) and inserted verbatim; empty text adds no argument at all. With `lpApplicationName` set, `CreateProcess` passes `lpCommandLine` to `cmd /c` as it is. With `lpApplicationName = nil` and a quoted path (FinalBuilder's call), Windows adds the outer quotes itself. So the library's form (`""<bat>" <raw>"`) gives the batch file what `CreateProcess(nil, '"<bat>" ' + raw)` does. This was measured byte for byte (`%*`, `%1`..`%9`) for `a b c`, `"x y" z`, `%PATH%`, `!x!`, `a&b`, `a^b`, `(a)`, `"unclosed` and `""`, with batch paths with and without a space (`BatchFile_UnsafeRaw_MatchesDirectCreateProcess`). Without the outer pair, every input containing a quote breaks.

## Reading output

Each redirected output stream has a `TIOInfo`:

- `QueueAsyncPipeRead` holds `Lock`, refuses to start a read once `Closing` is set, and calls `StartThreadpoolIo` + `ReadFile`. Transient out-of-resource errors are retried a few times inline.
- `IoCompletionCallback` marks the stream as `Delivering`, then `CompleteRead` delivers the data, pays off `Unread` (see step 3 of the teardown below) and queues the next read. When no read is pending (EOF, error, `Closing`) it sets `DoneEvent` as its very last action. The callback **never** calls `CloseThreadpoolIo`; the worker owns the lifetime.
- **`StartInfo.DeliverOnRunThread` (`HandOver`).** Here the callback only stores the byte count and result and sets `DataReady` (manual reset), as its very last action. The thread running the run calls `DispatchHandedOver` from its waits: the main wait in `DoWaitForCompletion` (whose `DataReady` events come after the process, terminate and cancellation handles, so those win) and `WaitForDrain`. It resets `DataReady`, then calls `CompleteRead` itself. Once the run timeout has elapsed the main wait looks only at the process, terminate and cancellation handles, so `DataReady` events that are signalled every time the wait is reached (stdout and stderr continuously busy) can't keep the timeout from being seen.
  - **Back-pressure.** The next read is queued only after delivery, so one buffer per stream is in flight, and a slow target backs up into the pipe rather than into memory.
  - **Done events.** Only `CompleteRead` (on that thread) sets `DoneEvent` in this mode, so once both are set nothing is left handed over.
  - **Close.** `CloseIO` delivers a buffer handed over but not yet delivered (an abandoned run, a drain that timed out).
- `IsMultiThread` is set in the unit initialization: callbacks run Delphi code on threadpool threads, and FastMM only locks when `IsMultiThread` is set.

## Teardown (`DoWaitForCompletion` → `ReleaseRunResources`)

1. Wait on the process handle, `FTerminateEvent`, the cancellation event or token, and the timeout. A synchronous `Execute` on the main thread also waits on `SyncEvent` and calls `ServiceSynchronize` (`CheckSynchronize`) when it is set, here, in `WaitForDrain` and in `CloseIO`: a target called on a threadpool thread may be inside `TThread.Synchronize`, waiting for this thread. Methods other threads queued run there too; one that raises is passed to `ApplicationHandleException` when assigned, otherwise logged, and never ends the run. The stdin writer is not covered: a source that calls `Synchronize` from `GetData` still blocks.
2. The outcome:
   - The child exited: `Exited` with its exit code.
   - Terminate or cancellation: `KillChild`, then `Terminated` with `TerminateExitCode` (default 9999). A child that has exited by then keeps `Exited` and its real exit code.
   - Timeout: `TimedOut = True`. The child is killed and the run reports `TimedOut` with `TimedOutExitCode` (default 8888); a child that exited right at the timeout reports `Exited` with its real code. With `TerminateOnTimeout = False` nothing is killed: the run is *abandoned* (Status `TimedOut`).
   - An unexpected wait result (`WAIT_FAILED`) means the child can no longer be monitored: it is killed and reported `Terminated`. An exception during the wait also kills it.

   `KillChild` calls `TSystemUtils.TerminateProcessTreeAndWait` with the child's handle and the job (if any):
   - **Collect.** A Toolhelp walk from the child finds every descendant (one created before its supposed parent is a recycled id and is skipped) and opens each one, before anything is ended. Nothing links a program to the tree only through a parent that has already gone, and the handles keep the ids from being reused.
   - **Kill.** Then `TerminateJobObject` (its result is not checked), then the descendants deepest first, then the child. The tree is walked with a job too, because a program started with `CREATE_BREAKAWAY_FROM_JOB` isn't in it.
   - **Wait.** Finally it waits, on the thread completing the run, up to 5 s in all for the child and every descendant to have gone, so a caller that checks for leftovers when `Execute` returns finds none.
   - **Tests and limits.** `Terminate_EndsBreakawayGrandchild` / `Terminate_EndsBreakawayChildOfAnInJobGrandchild` and `Terminate_DescendantsGoneWhenRunCompletes` pin these. The walk is not repeated for programs started while the kill runs: `NoJob_Terminate_EndsProgramsStartedDuringTheKill` (a helper starting programs from 4 to 16 threads) never caught one escaping a single walk.
   - **`TerminateProcessTree`.** It uses the same collect-then-kill walk without the job or the wait (`NoJob` without a run in progress: the `KillOnRelease` fallback at release).
3. Close an interactive stdin source, then wait for the stdout/stderr `DoneEvent`s (`WaitForDrain`), bounded by `PipeDrainTimeoutMS`. The stdin writer keeps going meanwhile (a descendant may still be reading) and is stopped in step 5. After a kill an `INFINITE` drain timeout is replaced by the 2000 ms default. An abandoned run skips this wait (the child still holds its pipe ends, so they would never reach EOF). The wait runs in 50 ms slices. After a normal exit, `Terminate` or cancellation ends it: the remaining I/O is cancelled in step 4, possible truncation is logged, and the job (if there is one) is terminated so what the child started stops too. Without a job nothing is killed, because the exited child's process id can't be trusted to find its children. After a kill, `Terminate` / cancellation / the timeout already caused it, so they don't end this wait early.
   After a normal exit, `RecordUnreadOutput` first takes `PeekNamedPipe`'s byte count for each pipe under the IO lock (`Unread`) and sets `CountReads`. Each read queued from then on is marked `ReadCounted`, and it pays off `Unread` only once its data has been delivered to the targets (the callback sets `Delivering`, `CompleteRead` clears it after `DeliverOutput`). The drain clock starts only once no unfinished stream still owes bytes, so the time a slow target spends on the child's own output doesn't count and can't produce a false "Output may be truncated" error. The read that was in flight when the child exited is never counted; if it completes after the clock has started (with a descendant's data), it is owed from then until it has been delivered, and the clock starts again. That happens at most once per stream, so such a drain can take about twice `PipeDrainTimeoutMS` plus the delivery time. The bookkeeping holds because a read that is in flight leaves nothing in the pipe, and no new read can be queued while the lock is held. A target that never returns already blocks `WaitForThreadpoolIoCallbacks` in step 4, so this adds no new way to hang.
4. `CloseIO`: set `Closing`, `CancelIoEx`, `WaitForThreadpoolIoCallbacks`, `CloseThreadpoolIo`, close the handles. On the main thread (and not with `DeliverOnRunThread`) it first waits for `DoneEvent`, servicing `SyncEvent` meanwhile, because `WaitForThreadpoolIoCallbacks` would otherwise wait for a callback that is itself waiting for this thread in `TThread.Synchronize`. Anything still pending at this point is held open by a descendant and gets cancelled; the timeout is logged as possible truncation.
5. `StopStdInWriter`: set the abort flag and repeat `CancelSynchronousIo` every 100 ms, for a writer blocked in `WriteFile` (a descendant holding stdin that never reads), for at most 1 s (`cCancelWaitMS`). A writer still running then is blocked in its source's `GetData`, which can't be cancelled: it is logged and left to finish on its own (see [Stdin writer](#stdin-writer)).
6. The base class then calls `Done` on every target and publishes the result.

## Stdin writer

Each run with redirected stdin gets a `TWindowsStdInWriter` (`TStdInWriter` in `VSoft.Process.Base.pas`). It owns the pipe's write end and holds the source, the abort flag and any error. The writer thread works on nothing else, so a writer that is abandoned in step 5 can't touch the next run's state, and the write end it closes is its own. The thread gets its own reference to the writer, and the writer holds a reference to the process, which stays alive until the thread finishes. The thread is created `CREATE_SUSPENDED` so `FStdInWriterThreadId` is set before it can run. When the writer finishes it clears that id with a compare-exchange, only if it is still its own. An error raised by the source is kept on the writer and logged by `StopStdInWriter`, so a writer left behind can't log into a later run.

## Detached launches

`DoExecuteDetached` uses `DETACHED_PROCESS | CREATE_BREAKAWAY_FROM_JOB`, or `CREATE_NEW_CONSOLE` in place of `DETACHED_PROCESS` with `StartInfo.DetachedNewConsole` (the console is shown or hidden by `wShowWindow`, from `HideWindow`). The console is never ours either way, so our Ctrl+C / Ctrl+Break never reaches the child. `CREATE_NEW_PROCESS_GROUP` is deliberately not used: it would make the child, and everything it starts, ignore Ctrl+C. When the host's job doesn't allow breakaway, CreateProcess fails with `ERROR_ACCESS_DENIED` and the launch is retried inside the job. With credentials it uses `CreateProcessWithLogonW` with the flags that API accepts. A detached launch ignores the pipes, `JobMode` and the timeout, creates no job and inherits no handles. `ProcessorAffinity` is applied, then the process and thread handles are closed and only the process and thread ids are kept.

## Credentials

`CreateProcessWithLogonW` is called with the child's ends left non-inheritable. The call goes to the Secondary Logon service, which can take seconds (loading a user profile); no lock is held for it, so it doesn't stall other launches in the host. Leaving the ends non-inheritable works because the service is not the child's real parent: it `DuplicateHandle`s the three `STARTUPINFO` std handles from the caller into the child (James Forshaw, Project Zero, "Exploiting a Leaked Thread Handle", the MS16-032 analysis), and the child inherits nothing else from us. Microsoft's documentation of the function has no `bInheritHandles` parameter and says nothing about inheritance. It only says the std handles are "copied unchanged to the child process without validation". So `TProcessLogonTests` checks both halves with real `LOGON_NETCREDENTIALS_ONLY` launches (a made-up user, which Windows doesn't check locally): `NetOnlyLogon_RedirectsStdOutAndStdErr` (non-inheritable pipe ends still reach the child) and `NetOnlyLogon_ChildInheritsNoOtherHandle` (an inheritable pipe end of ours is not inherited, with a `CreateProcess` control that is). `LogonLaunch_DoesNotBlockOtherLaunches` stubs `LaunchWithLogon` (protected virtual) to check that a plain launch is not held up by one in progress. `CreateProcessWithLogonW` can't be called from LocalSystem (Microsoft documents this); that is unchanged.

`CreateProcessWithLogonW` needs a domain or a UPN user name. Without either, `.` (the local account database) is passed. `LoadUserProfile` maps to `LOGON_WITH_PROFILE` and `NetCredentialsOnly` to `LOGON_NETCREDENTIALS_ONLY`. Validation rejects a UPN user name combined with a `Domain`, a user name in `DOMAIN\user` form (with or without a `Domain`: it is never split, so without one the logon would look for a local account of that whole name), a user name without a password, a domain or password without a user name (no logon would happen, so the child would run as the current user), and a command line longer than the 1024 characters the API accepts.
